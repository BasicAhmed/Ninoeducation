Feature: abandoned application recovery — capture and follow up on incomplete apply-wizard sessions

New application_drafts table, deliberately separate from the main
applications table rather than relaxing its NOT NULL constraints — a
draft is a fundamentally incomplete record (no license, no budget yet
at the point we can first reach someone) and shouldn't weaken the
data integrity guarantees the admin panel relies on for real
submissions.

How it works: saveApplicationDraft fires silently in the background
as a visitor progresses past the contact step in the apply wizard
(and again on later steps, enriching the same draft with license and
budget info as it becomes available), upserted by email so reloading
or restarting the wizard updates the same row instead of creating
duplicates. Never awaited, never blocks the wizard's own flow — wrapped
in a swallowed catch, since this is a best-effort recovery signal, not
something a visitor's experience should ever depend on. The moment
someone actually finishes and submits, submitApplication deletes their
matching draft, so the table always represents "currently abandoned,"
with no separate status flag needed.

New admin page at /admin/abandoned (with a nav entry) lists every
incomplete lead: name if given, contact info, which step they reached,
how long ago, and license/budget context if they got that far. Each
row has a one-click WhatsApp button with a warm, human opener ('saw
you started but didn't finish, need help with anything?') generated
the same wa.me-link way every other WhatsApp touchpoint on the site
already works, plus a dismiss action for leads not worth pursuing.

Real bug caught before shipping, not after: the first version of the
admin page put a confirm() dialog directly in a form's onSubmit inside
a Server Component page — React doesn't allow event handlers as props
there. Same category of mistake as one earlier in this project.
Extracted the dismiss button into a small client component instead.

Verified what's actually verifiable in this sandbox (no real database
access here): confirmed via the dev server log that the wizard
genuinely attempts to save the draft when advancing past the contact
step — the connection attempt is real, it just can't complete without
network access to the real database — and separately confirmed the
wizard itself proceeds to the next step completely unaffected when
that background save fails. Verified the admin page's rendering
directly with representative mock data (including a no-name/
partial-data row to check the fallback text and the phone-instead-of-
whatsapp fallback for the message link), then restored the real
database query and confirmed the restored file is byte-for-byte
identical to before the stub via a diff.
