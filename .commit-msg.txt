Translate all 12 guides, the guides index, and the cost calculator into English — completing the /en/ URL space for real content, not just chrome

Follow-up to the routing infrastructure from the previous commit.
That commit made /en/* a real, crawlable URL space, but explicitly
excluded guides, the calculator, and the guides index from the
sitemap because their actual body content was still hardcoded Arabic
— visiting /en/guides/anything would have shown English chrome
wrapping an entirely Arabic article, which is worse for SEO than not
having the URL at all.

This commit does the actual translation work:

- All 12 individual guides fully translated, not just retitled —
  every section, list, table, and FAQ answer, preserving the same
  structure, internal cross-links (now correctly pointing to /en/
  equivalents), and JSON-LD Article/FAQPage schema per language.
- lib/guides.ts restructured to carry titleAr/titleEn and
  descriptionAr/descriptionEn for every guide, since the homepage's
  guide cards and the guides index both pull from this single source.
- components/GuideArticle.tsx (the shared wrapper every guide uses)
  now takes a lang prop and translates its own chrome — the FAQ
  heading, related-guides heading, and final CTA were hardcoded
  Arabic before, which would have leaked into every English guide
  otherwise.
- components/GuidesSearch.tsx fully bilingual, including the actual
  search/filter logic matching against the right language's title
  and description depending on which language is active.
- The cost calculator (component and page) converted from 100%
  hardcoded Arabic to a proper bilingual COPY object — this was a
  fully separate, standalone piece of hardcoded content, not part of
  the guides system at all.
- Sitemap updated to add /en/ entries for the calculator, guides
  index, and all 12 guides now that they're genuinely bilingual.

Real bug caught during this session, not shipped blind: my first
lint-fixing pass used a blanket regex to escape apostrophes for JSX
(react/no-unescaped-entities), but applied it to the entire file
rather than only the actual JSX-returning content functions — it also
escaped apostrophes inside plain JS string constants (FAQ_ITEMS, the
kicker/title/intro values, META), which don't need HTML entity
escaping at all. Since those are plain JS strings rendered via {},
not JSX text nodes, React doesn't interpret &apos; there — it prints
the six literal characters on the page. Caught this by actually
loading the rendered page and reading it, not by trusting a clean
lint result, since the lint was clean both before I introduced this
and after I fixed it (the linter only checks JSX text, not string
content). Fixed with a second, more precise pass that only reverts
entity-escaping outside the actual JSX content functions, verified
directly on the rendered page afterward (the literal "&apos;" text is
gone, real apostrophes render correctly) — and then re-verified across
all 12 guides via a scripted sweep checking every guide's rendered
body text for leftover entity artifacts, not just the two I first
spot-checked.

Verified beyond the entity fix: confirmed every one of the 12 guides
plus the calculator, guides index, and pillar guide return 200 in
both the bare and /en/-prefixed URL, confirmed the Arabic versions
render identically to before this session (no regression from all the
file rewrites), confirmed the sitemap now contains exactly the 21
expected /en/ URLs via direct inspection of the generated XML, and
confirmed the homepage's one slow response in testing was the same
known sandbox database-connection-timeout pattern seen throughout
this project, not a new issue — the actual server log shows it
completed successfully (200) after the fallback path in
getPublishedSchools/getPublishedAccommodations caught the connection
error, just slower than a single test's timeout window allowed.
